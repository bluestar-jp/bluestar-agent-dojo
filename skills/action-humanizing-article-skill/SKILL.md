# Article Humanization Skill (AI-ness Removal)

- Purpose: AI生成文章特有のパターンを検出し、人間らしい自然な日本語に変換する
- Scope: テンプレ感、説明書感、記号過多、過剰な丁寧さの除去

## 入力形式

```json
{
  "draft_article": {
    "frontmatter": {...},
    "content": "<全段落を統合したMarkdownテキスト>",
    "sections": [...]
  }
}
```

## 検出ルール

### ルール1: 内容ルール（Content Rules）

#### 1.1 前置き宣言の禁止

**検出パターン**:

- `Grep: "本記事では|今回は|以下では|この記事では|見ていきましょう|見ていきます"`

**書き換え方針**:

- 宣言を削除し、直接内容に入る
- 問題提起や具体例から始める

**例**:

```text
❌ 「本記事では、Reactのパフォーマンス最適化について解説します。」
✅ 「Reactアプリケーションが遅い。ページの読み込みに3秒かかる。」
```

#### 1.2 安全クッションの削除

**検出パターン**:

- `Grep: "かもしれません|と考えられます|一般的に|多くの場合|通常は|基本的に|原則として|の可能性があります|することが推奨されます"`

**書き換え方針**:

- 断定形に変換（「〜です」「〜します」）
- 具体的な条件や理由を添える

**例**:

```text
❌ 「一般的に、キャッシュを使うことでパフォーマンスが向上する可能性があります。」
✅ 「キャッシュを使うとレスポンス時間が50%短縮される。」
```

#### 1.3 抽象語の空回り排除

**検出パターン**:

- `Grep: "重要です|効果的|最適|有用|優れた|便利"`（文末に来る場合）

**書き換え方針**:

- なぜ重要/効果的なのか具体的に説明
- データや具体例で裏付ける

**例**:

```text
❌ 「型安全性は重要です。」
✅ 「型安全性がないと、本番環境でランタイムエラーが発生する。」
```

#### 1.4 同義語の言い換え連打禁止

**検出パターン**:

- 連続する文で同じ内容を異なる語彙で繰り返す（手動検出）

**書き換え方針**:

- 最も適切な表現を1つ選ぶ
- または具体的な理由に展開する

#### 1.5 前提の繰り返し禁止

**検出パターン**:

- `Grep: "前述の通り|先ほど述べたように"`が頻出

**書き換え方針**:

- 最初に一度定義したら、以降は単純に使用
- 「これ」「この手法」等で参照

### ルール2: 記号・表記ルール（Symbol & Format Rules）

#### 2.1 Markdown記法の禁止（本文中）

**検出パターン**:

- 段落内に**太字**が3つ以上
- `インラインコード`が技術用語以外にも適用

**書き換え方針**:

- 太字は本当に重要な1-2箇所のみ
- インラインコードは実際のコードやコマンドのみ

#### 2.2 括弧の乱用禁止

**検出パターン**:

- `Grep: "\(.*?\)"`で括弧を抽出、1段落に2つ以上は警告

**書き換え方針**:

- 補足は別の文として記述
- または文中に自然に織り込む

**例**:

```text
❌ 「Reactのフック（useState、useEffect等）を使うことで、状態管理（ステート管理）が簡単になります（特に初心者には便利です）。」
✅ 「Reactのフックを使うと状態管理が簡単になる。useStateやuseEffectは初心者にも使いやすい。」
```

#### 2.3 コロンとスラッシュの制限

**検出パターン**:

- `Grep: "[:：]"`（見出し以外）
- `Grep: " / "`

**書き換え方針**:

- コロンを削除し、普通の文にする
- スラッシュは「と」や「、」に置き換える

#### 2.4 箇条書きの節度

**検出パターン**:

- 2項目だけの箇条書き
- 箇条書きが5つ以上連続
- 各項目が長文（3行以上）

**書き換え方針**:

- 2項目は文中に織り込む
- 長文項目は段落に分割

### ルール3: リズムルール（Rhythm Rules）

#### 3.1 文のリズムを不均一に

**検出パターン**:

- 連続する5文以上が同じ文字数（±10%以内）
- すべての文が「〜です。」で終わる

**書き換え方針**:

- 短い文と長い文を織り交ぜる
- 終助詞を変化させる（「〜だ」「〜である」「〜する」）

#### 3.2 段落の冒頭を多様化

**検出パターン**:

- 連続する3段落以上が同じ構造で始まる

**書き換え方針**:

- 動詞から始める段落を挿入
- 疑問文や命令文で始める段落を追加

### ルール4: トーンルール（Tone Rules）

#### 4.1 過剰な説明口調の削除

**検出パターン**:

- `Grep: "とは、.*のことを指します|と定義されています|という概念があります"`

**書き換え方針**:

- シンプルに「〜は〜だ」
- または具体例から定義を示す

#### 4.2 丁寧すぎる敬体の排除

**検出パターン**:

- `Grep: "してみましょう|してください|していただけます"`

**書き換え方針**:

- 「〜する」「〜できる」に変換
- または「〜してほしい」「〜すべきだ」

## ワークフロー

### Step 1: パターン検出

1. `Grep`を使用して各ルールの違反パターンを検索
2. 各問題箇所に違反ルールをタグ付け
3. 段落ごとに違反箇所をリストアップ

### Step 2: 重要度判定

- **high**: 複数のルール違反が集中、AIっぽさが顕著
- **medium**: 単一ルール違反だが頻出
- **low**: 単発の違反、影響が限定的

### Step 3: 書き換え実行

1. 元の意味を保持しながらルールに従い修正
2. 文字数は±20%以内に収める
3. 段落構成は維持（段落の結合・分割は最小限）

**書き換え例**:

```markdown
# 元の段落（P1）
本記事では、Reactのパフォーマンス最適化について解説します。一般的に、React.memoを使うことで再レンダリングを防ぐことができます。これは重要です。

# 書き換え後（P1）
Reactアプリケーションが遅い。ページの読み込みに3秒かかる。React.memoを使うとレンダリング回数が半分になる。ベンチマークでは、1000回のレンダリングが500回に削減された。
```

### Step 4: 検証

- 修正後の文章を読み上げて自然さを確認
- 技術的正確性を維持しているか確認
- 元の情報が失われていないか確認

## 重要度の判断基準

- **high**: 複数のルール違反が集中、AIっぽさが顕著で読者が違和感を感じる
- **medium**: 単一ルール違反だが頻出、改善すると自然さが向上
- **low**: 単発の違反、影響が限定的

## 書き換えの制約

### 保持すべき要素

- 技術的正確性
- キーポイント（元の主張や情報）
- 段落構成（段落の数と順序）
- コードブロックの内容

### 変更可能な要素

- 文の順序（段落内）
- 語彙の選択
- 文の長さとリズム
- 記号の使用

### 文字数の制約

- 元の文字数の±20%以内に収める
- 大幅な削減や追加は避ける

## 自己修正

### 書き換えが困難な場合

- 技術的正確性が不確実なら、元の表現を保持
- 文字数制約を超える場合、優先度の高いルールのみ適用
- 判断が難しい場合、suggestionのみ提示（書き換えなし）

### 誤検知の可能性

- 意図的な強調や括弧の場合、理由を確認
- 専門用語の定義文は「とは」の使用が適切
- コード説明では丁寧な表現が適切な場合あり
