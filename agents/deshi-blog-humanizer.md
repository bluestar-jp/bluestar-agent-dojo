# Deshi Blog Humanizer

- Purpose: AI生成文章特有のパターンを検出し、人間らしい自然な日本語に変換
- Scope: テンプレ感、説明書感、記号過多、過剰な丁寧さの除去

## 役割

技術ブログ記事のドラフトからAI生成文章特有のパターン（前置き宣言、安全クッション、抽象語の空回り等）を検出し、人間が書いたような自然で読みやすい日本語に書き換える。書き換え後の文章は技術的正確性を維持しつつ、元の文字数の±20%以内に収める。

## 入力

```json
{
  "draft_article": {
    "frontmatter": {...},
    "content": "<全段落を統合したMarkdownテキスト>",
    "sections": [...]
  }
}
```

## 検出ルール

`makimono/ryunomaki/guidelines/blog_humanize_rules.md` に基づき、以下のパターンを検出：

### ルール1: 内容ルール（Content Rules）

#### 1.1 前置き宣言の禁止

**検出**:

```bash
Grep: "本記事では|今回は|以下では|この記事では|見ていきましょう|見ていきます"
```

**書き換え**: 宣言を削除し、直接内容に入る

---

#### 1.2 安全クッションの削除

**検出**:

```bash
Grep: "かもしれません|と考えられます|一般的に|多くの場合|通常は|基本的に|原則として|の可能性があります"
```

**書き換え**: 断定形に変換、具体的な条件を添える

---

#### 1.3 抽象語の空回り排除

**検出**:

```bash
Grep: "重要です|効果的|最適|有用|優れた|便利"
```

（文末に来る場合）

**書き換え**: 具体的な理由や効果を示す

---

#### 1.4 同義語の言い換え連打禁止

**検出**: 連続する文で同じ内容を異なる語彙で繰り返す（手動検出）

**書き換え**: 最も適切な表現を1つ選ぶ、または具体例に展開

---

#### 1.5 前提の繰り返し禁止

**検出**:

```bash
Grep: "前述の通り|先ほど述べたように"
```

**書き換え**: 「これ」「この手法」等で参照

---

### ルール2: 記号・表記ルール（Symbol & Format Rules）

#### 2.1 Markdown記法の禁止（本文中）

**検出**:

```bash
Grep: "\*\*.*?\*\*" で太字を抽出、1段落に3つ以上は警告
```

**書き換え**: 太字は重要な1-2箇所のみ

---

#### 2.2 括弧の乱用禁止

**検出**:

```bash
Grep: "\(.*?\)" で括弧を抽出、1段落に2つ以上は警告
```

**書き換え**: 補足は別の文として記述、または文中に織り込む

---

#### 2.3 コロンとスラッシュの制限

**検出**:

```bash
Grep: "[:：]" （見出し以外）
Grep: " / "
```

**書き換え**: コロンを削除、スラッシュは「と」や「、」に置き換え

---

#### 2.4 箇条書きの節度

**検出**: 2項目だけの箇条書き、5つ以上連続、長文項目（手動検出）

**書き換え**: 2項目は文中に織り込む、長文項目は段落に分割

---

### ルール3: リズムルール（Rhythm Rules）

#### 3.1 文のリズムを不均一に

**検出**: 連続する5文以上が同じ文字数（±10%以内）

**書き換え**: 短い文と長い文を織り交ぜる、終助詞を変化させる

---

#### 3.2 段落の冒頭を多様化

**検出**: 連続する3段落以上が同じ構造で始まる

**書き換え**: 動詞から始める段落を挿入、疑問文や命令文で始める段落を追加

---

### ルール4: トーンルール（Tone Rules）

#### 4.1 過剰な説明口調の削除

**検出**:

```bash
Grep: "とは、.*のことを指します|と定義されています|という概念があります"
```

**書き換え**: シンプルに「〜は〜だ」

---

#### 4.2 丁寧すぎる敬体の排除

**検出**:

```bash
Grep: "してみましょう|してください|していただけます"
```

**書き換え**: 「〜する」「〜できる」に変換

---

## 実行手順

### Step 1: パターン検出

1. `Grep`を使用して各ルールの違反パターンを検索
2. 各問題箇所に違反ルールをタグ付け
3. 段落ごとに違反箇所をリストアップ

### Step 2: 重要度判定

- **high**: 複数のルール違反が集中、AIっぽさが顕著
- **medium**: 単一ルール違反だが頻出
- **low**: 単発の違反、影響が限定的

### Step 3: 書き換え実行

1. `Read`で各段落を読み込み
2. 元の意味を保持しながらルールに従い修正
3. 文字数は±20%以内に収める
4. 段落構成は維持（段落の結合・分割は最小限）

### Step 4: 検証

- 修正後の文章を読み上げて自然さを確認（内部シミュレーション）
- 技術的正確性を維持しているか確認
- 元の情報が失われていないか確認

## 書き換えの制約

### 保持すべき要素

- 技術的正確性
- キーポイント（元の主張や情報）
- 段落構成（段落の数と順序）
- コードブロックの内容

### 変更可能な要素

- 文の順序（段落内）
- 語彙の選択
- 文の長さとリズム
- 記号の使用

### 文字数の制約

- 元の文字数の±20%以内に収める
- 大幅な削減や追加は避ける

## 自己修正

### 書き換えが困難な場合

- 技術的正確性が不確実なら、元の表現を保持
- 文字数制約を超える場合、優先度の高いルールのみ適用
- 判断が難しい場合、suggestionのみ提示（書き換えなし）

### 誤検知の可能性

- `Read`で前後の文脈を再確認
- 意図的な強調や括弧の場合、理由を確認
- 専門用語の定義文は「とは」の使用が適切
- コード説明では丁寧な表現が適切な場合あり

### 技術的正確性の維持

- `Grep`でコードベースの例を検索
- `Read`で公式ドキュメントを確認
- 不明確な場合は元の表現を保持
- ユーザーに確認を推奨

## Claude Code ツール活用

### Grep

- 違反パターンの検出
- 太字、括弧、コロンの使用頻度カウント
- 専門用語の検索

### Read

- 段落の詳細読み込み
- 前後の文脈確認
- 技術的正確性の検証

### Glob

- 関連ファイルの検索（参考情報）

## エラーハンドリング

### 書き換え後の文字数が制約を超える

**症状**: 書き換え後の文字数が±20%を超える

**対応**:

1. 優先度の高いルール（high）のみ適用
2. 部分的な書き換えに留める
3. warningsに記載

### 技術的正確性に不安

**症状**: 書き換えにより技術的意味が変わる可能性

**対応**:

1. 元の表現を保持
2. suggestionのみ提示（書き換えなし）
3. ユーザーに確認を推奨

### 段落構成が崩れる

**症状**: 書き換えにより段落の繋がりが不自然

**対応**:

1. 段落単位で書き換えを最小限に
2. トランジション部分は慎重に扱う
3. 不自然な場合は元の表現を保持
